## 0. Draft'ın (WIP-4) ana fikirleri — alıntıların "neye katkı" ölçütü

- A1 Üç scheduler (OS → executor → GPU stream), tek bakış noktası yok.
- A2 Model verili analizler vs model çıkaran araçlar; kesişim boş.
- A3 Model ölçümden gelmeli, tasarım ≠ dağıtım.
- A4 FISH graph ⟨H, EX, N, E, F⟩ + doğruluk sözleşmesi (C1/C2), kimlik = handle + ömür.
- A5 Gözlemci sorunu: 5 dispatch türü, GPU'yu launch'ı bozmadan sarma, stable sinyali, T_valid, probe effect.
- A6 Fazlar (uygulama + GPU) → metrik ve maliyet ancak faz içinde karşılaştırılabilir.
- A7 Ölçülmüş modelin gösterdikleri: upstream'in görmediği dispatch, join rol-bimodalitesi, callback ≠ task, ortak omurga + varyant.
- A8 Roadmap: IR → SAG, LiME baseline, sched_switch deneyi.

## 2. Makale makale: katkı, alıntılar, bizim tezle ilişkisi

### casini-19-reservationbased — Casini, Blaß, Lütkebohle, Brandenburg, ECRTS 2019

**Kategori:** ANA (model verili). **Ne yapıyor:** ROS 2 "Crystal" tek-thread executor'ının davranışını kaynak kod incelemesiyle çıkarıp deneyle doğruluyor (readySet, polling point, processing window; öncelik = callback türü × kayıt sırası; timer'lar polling'e tabi değil). Bunun üstüne CPA esinli response-time analizi: her executor bir reservation server'a bağlı (sbf), callback'ler WCET e_i + arrival curve ile verili, callback grafı D sabit, DDS gecikmesi tek sabit δ. Alt zincirler (tek reservation içinde) bütüncül analiz edilerek "pay-burst-only-once" iyileştirmesi. Vaka: move_base, pyCPA.

**Bizim tezle ilişkisi:** İki katman (OS reservation + executor), üçüncü katman yok. Model "verili" ve tasarım zamanı: WCET'ler Bosch vaka çalışmasından gözlem, arrival curve'ler tasarım. Waitable'ı "henüz kullanan yok" diye analiz dışı bırakıyor; bugün intra-process ve NITROS yolu tamamen waitable. Sabit graf varsayımı bizim ömür-penceresi kimliğiyle (fini tracepoint'leri) çelişen bir sadeleştirme. GPU hiç yok (related work'te yalnız Suzuki'nin ROS 1 CPU/GPU koordinasyonu anılıyor).

**Alıntılar (birebir):**
- A1: "While the scheduling model of operating systems like Linux has been studied extensively, this is not the case for ROS. Even though it is a middleware layer and not a proper operating system, its effects on an application's runtime behavior are substantial, rivaling or even exceeding that of the underlying OS." (§1)
- A1: "Consequently, applications running on top of ROS are subject to the scheduling decisions of the underlying operating system and the middleware layer, with complex and interdependent effects on timing." (§1)
- A3: "Although the end-to-end latency problem is well-studied in the literature, existing work often assumes idealized scheduling models that are not always directly applicable in real systems." (§1)
- A2/A3: "ROS developers therefore have to resort to fully prototyping and deploying a design to measure its timing properties, which severely limits the degree to which the design space can be explored in practice." (§1)
- A3: "While this greatly simplifies and speeds up robot development, it also obfuscates the overall timing behavior. This problem is further aggravated by ROS' event-driven design style, which gives rise to data dependencies and potentially long processing chains." (§1)
- A3 (en güçlüsü — kendi modelleri bile kod incelemesinden, hata payını itiraf ediyorlar): "The presented description of the ROS scheduler is based on manual code inspection. In a system as complex as ROS, however, this is potentially error-prone, as there might be subtle interactions that are easily overlooked yet change the behavior drastically." (§3)
- A3: "ROS places great emphasis on modularity and composability. It therefore encourages strict separation between the logical structure of the application and the mapping of this structure onto hosts, processors, and threads. While the former is defined by the package developer, the latter is entirely up to the system integrator." (§2.1)
- A4 (sabit graf varsayımı): "We assume the graph D to be fixed, i.e., callbacks can neither join nor leave the system at runtime." (§4)
- A5 (dört tür, 2019): "The executor distinguishes four categories of callbacks: timers, ..., subscribers, ..., services, ..., and clients, which are triggered by responses to service requests." (§3)
- A5/A7 (waitable analiz dışı): "In addition to topics and services, ROS also provides a waitable callback type. ... Since this mechanism was only introduced in the latest release, there are no known users of this mechanism as of now. It will be necessary to extend our analysis to these additional methods as and when they are adopted in ROS 2." (§8)
- A7 (oort ↔ event source; draft'ta tırnaksız kullanılan cümle): "To integrate such events in our ROS model, we allow external threads to interact with ROS and model them as pseudo-callbacks. Specifically, we name these threads event sources. An event source is a regular OS-level thread that is sporadically activated, and interacts with ROS by publishing to one or more topics, thus acting as an interface or ingress point for external events." (§4)
- A8 (self-suspension / SAG yolu): "chains crossing multiple reservations could be modeled by means of self-suspending tasks [16]." (§8)
- Model olgusu: "Overall, the pair (callback type, registration time) is a unique priority for each callback." (§3)
- Model olgusu (MT executor dışarıda): "This paper considers the built-in single-threaded ROS executor. ... Extending our analysis to handle blocking relationships among callbacks remains future work." (§8)
- Karşıtlık (tasarım zamanı vs dağıtım zamanı): "Without implementing a single line of ROS code, we are able to reason about the worst-case latencies of two quite different move_base designs" (§6)

### blass-2021-starvation — Blaß, Casini, Bozhko, Brandenburg, RTSS 2021

**Kategori:** ANA (model verili; ama modelin parametreleri ROS-Llama ile runtime'da ölçülmüş). **Ne yapıyor:** Casini'19'un tek-thread executor modelini alır, altı özellikle formalize eder (SQ sıralılık, NP preemptsiz, WC iş-koruyan, PP polling point, SM örnekleme, PR seçici öncelik) ve üç iyileştirme getirir: (1) execution-time curve ET_i(n) ile ardışık n instance'ın toplu talebi; (2) busy-window içinde executor-içi aktivasyon eğrileri; (3) round-robin analizi: processing window başına her polled callback'ten en fazla bir instance koşar, bu yüzden burst'ler sınırlı etkiler. İki analiz (RR ve BW) birbirini domine etmez, minimumları alınır. Değerlendirme: sentetik graf + Nav2 (Turtlebot 3) grafı; 80×'e varan sıkılaşma, ET-curve'ün tek başına 60× katkısı.

**Bizim tezle ilişkisi:** Analizin girdisi olan graf ve parametreler *ölçümden* geliyor (ROS-Llama'nın introspection'ı, Turtlebot'ta runtime), yani "analizciler modeli verili alır" cümlesi doğru ama "ölçülmemiş" anlamına gelmez: Brandenburg grubu extraction + analysis'i CPU-only olarak zaten bir boru hattı yapmış. Bizim ayrım cümlesi bunu bilerek kurulmalı ("CPU-only, thread/executor düzeyi, GPU segmenti yok"). İki seviyeli hiyerarşi burada açıkça yazılı; üçüncü seviye yok. Waitable yok; service ve client callback'leri subscription ile özdeş sayılıyor. Steady-state varsayımı (callback'ler katılmaz/ayrılmaz). Execution-time curve fikri bizim "join'de role göre bimodal WCET" ve "GPU varyant şekilleri" bulgularıyla doğrudan konuşuyor: tek skaler WCET'in aşırı pesimizmini onlar da 60× ile gösteriyor.

**Alıntılar (birebir):**
- A1 (iki seviye, açıkça): "Callbacks are subject to hierarchical scheduling at two levels. The first level of scheduling is the operating system scheduler, which schedules all executor threads as well as any unrelated threads. ... The second level of scheduling is performed by each executor when it selects the next instance to run." (§III)
- A1: "Second, callbacks are multiplexed onto shared executor threads, which execute callbacks using a custom scheduling policy that differs significantly from common real-time schedulers. The analysis thus not only has to consider the scheduling of executor threads by the OS, but also callback sequencing within executors." (§I)
- A7 (WCET tek skaler değil; join bimodalitesi ve GPU varyantları için): "In contrast, ROS callbacks often exhibit highly variable execution times [6], which are poorly represented by a single scalar." (§I)
- A7: "Since callbacks typically execute different code paths depending on the contents of the messages, they can exhibit varying execution-time patterns over time [6]." (§III)
- A7 (pesimizm büyüklüğü): "the response-time bounds of the WCET-based version of this-paper differ from the execution-time curve version by a factor of 60×. Assuming that each callback instance runs for its full WCET obviously leads to tremendous pessimism in the analysis of this callback." (§VI)
- A2/A3 (analizin modeli ölçümden geliyor): "The model stems from prior work [6], where it was obtained by measuring all model-relevant parameters (such as execution-time curves and activation frequencies) at runtime on a Turtlebot 3 robot performing a simple navigation task." (§VI)
- A3 (model sürümle değişiyor; kod incelemesine güven sınırlı): "In versions up to ROS 2 'Dashing,' timers are privileged but all other classes are polled [3]. In later versions, timers are polled callbacks as well [9]." (§II)
- A4 (sabit küme varsayımı): "We assume a steady-state system (i.e., callbacks neither leave nor join the system at runtime)" (§III)
- A5 (dört tür, waitable yok): "First, it prioritizes callbacks by kind: timers are inherently prioritized over subscriptions, which are prioritized over service handlers, which in turn are prioritized over clients. Second, it does not consider all pending callbacks as eligible for execution. ... Third, the executor executes at most one instance of each polled callback per processing window, irrespective of the number of queued activations." (§II)
- A5 (client = subscription sayılıyor): "From the perspective of the ROS scheduler, these callbacks behave identically to regular subscription callbacks. We thus do not distinguish between topics and services in this paper" (§II)
- A7 (oort ↔ event source): "Some of the inputs of a ROS system usually come from outside the callback system, for example, devices. This is commonly implemented through external driver threads that convert external stimuli into ROS publications. For consistency, we model such threads as executors with a single pseudo-callback." (§III)
- COTS duruşu (bizimle aynı): "In contrast, our focus is mainline ROS as it is deployed by most ROS users today." (§VII)
- Related work'te ROS-Llama'nın tanımı: "Also targeting unmodified mainline ROS deployments, Blass et al. [6] proposed an automated, introspection-based method for provisioning ROS executors under reservation-based scheduling." (§VII)

### blass-2021-rosllama — Blaß, Hamann, Lange, Ziegenbein, Brandenburg, RTAS 2021 (ROS-Llama)

**Kategori:** EXT + ANA + yönetim. Bizim için en yakın "boru hattı" öncülü: tracepoint'le çıkarım → analiz → provisioning, hepsi CPU-only. **Ne yapıyor:** Sistem entegratöründen yalnız zincir başı/sonu + hedef gecikme + degradasyon sırası ister. Model extractor rclcpp ve rcl'yi enstrümante eder (callback kayıt/başlangıç/bitiş/publish, thread'in executor olması, servis tespiti), callback kimliği = callback nesnesinin sanal adresi, execution time = per-thread CPU-time clock, arrival = monotonic clock; event source'lar "callback başlatmadan publish eden thread'ler" olarak bulunur. Budget manager Casini'19 analiziyle (ET⁺ eğrileriyle değiştirilmiş) reservation bütçelerini heuristik arar, SCHED_DEADLINE partitioned uygular; sistem 6 s'de bir "ardışık statik sistemler" olarak yeniden provizyonlanır. Pratik dersler: AMCL/tf döngüsü (sanal cycle-breaker topic), skaler WCET'in 56 ms vs ET⁺(40)=122 ms pesimizmi, message filter'ların (join) modellenememesi, DDS'in kara kutu olması, tf backlog patlamaları, davranış ağacını polling timer'ın gizlemesi.

**Bizim tezle ilişkisi:** "Extraction yarısı dolu" cümlesinin Abaza'dan da eski kanıtı (2021). Aynı zamanda FISH'in yaklaşımının aynısı: rclcpp/rcl'ye tracepoint, üçüncü taraf kaynağa dokunmadan. Farklar bizim lehimize yazılmalı: (i) yalnız C++ ve tek-thread executor, dört callback türü, waitable/intra-process yok; (ii) execution time CPU-time clock ile ölçülüyor → GPU beklemesinde thread'in tükettiği CPU süresi sayılır, bekleme dışarıda kalır (sched_switch deneyinin ROS-Llama karşılığı; unsound-on-GPU argümanı için birebir dayanak); (iii) callback kimliği = sanal adres, "ömür boyunca değişmez" varsayımı — bizim handle geri dönüşümü bulgusu bunu doğrudan çürütüyor; (iv) message filter/join ve polled okuma modellenemiyor diyorlar — bizim join-semantiği ve polled-subscription bulguları tam bu boşluk; (v) DDS kara kutu — biz rmw_take source_timestamp ile hop gecikmesini ölçüyoruz; (vi) gözlemci maliyeti %30–40 CPU, LTTng ile düşer diyorlar — bizim probe-effect ölçümü bu yolun devamı.

### 3.2 İddia (i): "analizciler modeli verili kabul ediyor"

**Yapı için tutuyor.** Yedi analiz makalesinin hepsinde chain/DAG, callback→executor ataması, öncelikler ve callback group üyeliği girdi; hiçbiri yapıyı çalışan sistemden almıyor (Blaß'21 vaka çalışmasında ROS-Llama'nın çıkardığı Nav2 grafını kullanıyor, ama analiz yapıyı verili sayıyor). Survey'in kendi cümlesi bunu söylüyor: "Applying formal real-time theory often requires detailed, static knowledge of the system … This approach is sometimes impractical for ROS 2 applications, which rely on reusable 'black box' components".

**Parametreler için inceltilmeli.** Survey Tablo 1'de yalnız bir iş "Measured" görünüyor ama metinler farklı söylüyor: Tang'20 ACET/WCET "observed … in 10,000 runs" (yöntem yok), Tang'23 "profiled on Intel CPU" (yöntem yok), Teper'24 ros2_tracing tabanlı ölçüm, Blaß'21 ROS-Llama ölçümü. Yani analizciler parametreleri zaten ölçüyor, ama ölçüm yöntemi ya belirtilmiyor ya ad hoc. Bu, A2'yi zayıflatmaz, A3/A5'i güçlendirir: **sorun "ölçmüyorlar" değil, "ölçümün ne gördüğü (CPU süresi mi, GPU beklemesi dahil mi, hangi fazda) tanımsız"**. WiP'te cümle: "structure is given by hand and parameters are measured by means the papers rarely specify".

**Analiz varsayımları ile ölçtüklerimiz.** Aşağıdakiler bu okumada tespit edilen, deployment ölçümümüzle doğrudan çelişen ya da sınanabilir varsayımlar; A7 bulguları bunlara bağlanmalı:

| executor = OS süreci | Wu §4.1 | 8 süreçte 15 executor (AAS) |
| MT executor'da her thread ayrı core + reservation | Sobhani §III-B | thread sayısı = hardware_concurrency (6 P-core'a 20 thread), reservation yok |

### 3.3 İddia (ii): "model çıkaranlar üç katmandan yalnız birine dokunuyor"

**Bu hâliyle yanlış; düzeltilmeli.** ROS-Llama (2021) hem executor katmanını (rclcpp/rcl tracepoint'leriyle callback grafı) hem OS katmanını (per-thread CPU-time saati, SCHED_DEADLINE bütçeleri) görüyor; Abaza (2024) callback + sched_switch; LiME yalnız thread; LiMEIT yalnız intra-thread (ST executor). Doğru ifade: **"extractors cover at most the OS and executor layers; none observes the GPU layer, and none observes multi-threaded executors."** Ayrıca:

- "Framework-aware tracepoint extraction" 2021'de ROS-Llama'yla kurulmuş; draft bunu Abaza'ya bağlıyor, düzeltilmeli. FISH'in framework-aware tarafındaki yeniliği: beş executable türü (client/waitable dispatch dahil), kimlik = handle + ömür, C1/C2 kontratı, intra-process hop görünürlüğü, MT executor, GPU attribution, fazlar.
- ROS-Llama'nın per-thread CPU-time saati ve Abaza'nın sched_switch segmentleri aynı şeyi yapıyor: GPU beklemesini "execution time" dışında bırakıyor. LiMEIT ise uprobe ile "start–end arasında tüketilen CPU süresi" ölçüyor (§III-F) — aynı kör nokta. Bu, A8'deki sched_switch deneyinin üç hedefi olduğunu gösterir; deney tek bir araca değil, ölçüm ilkesine (CPU-time vs wall-time + GPU segment) karşı kurulmalı.
- LiMEIT'in framework-specific araçlara eleştirisi (sürüme bağımlı, framework uzmanlığı, kaynak/araç değişikliği, klasik model üretmeme) WiP'te açıkça cevaplanmalı: Humble'a bağlıyız; uygulama kaynağına değil rclcpp overlay'ine dokunuyoruz; çıktı IR ve SAG job set'e emitter var (A8).
- LiMEIT'in üç sınırı (yalnız ST executor; release gözlenemez → belirsizlik penceresi; yalnız koşan task'lar bulunur) FISH'in üç somut avantajı (MT executor; middleware olaylarıyla release/hop; init kaydıyla zero_exec). Bunlar WiP'te tek cümlede verilmeli.

### 3.4 İddia (iii): "kesişim boş"

**Tutuyor.** Hiçbir extractor GPU katmanını görmüyor; hiçbir ROS 2 analizi GPU segmenti almıyor (Sobhani ve survey açıkça future work); GPU-RT hattı (Amert/Otterness/Bakita) middleware görmüyor; Holoscan RTA serisi (okunmadı, konuşma notuna göre) model-verili ve ROS 2 değil; PAAM/ROSGM yönetim katmanı ekliyor, model-verili. Survey'in "iki-seviyeli scheduling hiyerarşisi" cümlesi ile Wu survey'inde GPU'nun hiç geçmemesi, A1'in "üçüncü scheduler görünmez" tezini iki survey'in ağzından kanıtlıyor.

**Ama "ilk" iddiası kurulmamalı;** konuşma notunun sonucu geçerli: novelty kesişimde ve "birleştirince ne bozuluyor" sorusunun cevabında. Okumadan çıkan somut "bozulan" şeyler: (a) CPU-time tabanlı execution time ölçümü GPU beklemesini dışlar (ROS-Llama, Abaza, LiMEIT); (b) analizlerin executor varsayımları (thread=core, executor=süreç, δ=0) deployment'ta tutmaz; (c) OR-activation join modeli sync-join'i yanlış sayar; (d) sürüm kayması (Dashing→Foxy timer, Jazzy FIFO) ölçülmeden yakalanamaz; (e) model üzerinde optimizasyon ölçülen gecikmeyi artırabilir (Teper'24).

### 3.5 Diğer ana fikirler için literatür durumu

- **A3 (tasarım ≠ dağıtım):** Yetkili cümle LiMEIT'te ("models recovered from its implementation reflect how it actually is behaving … lest they silently diverge"); Bakita'24 GPU tarafında ("false assumptions lead to the failure of analytical response-time bounds"); Tang'20 §VII-B model sapmasını görüp deneyi modele uydurmuş (tek core'a bağlama) — en çarpıcı anekdot; Wu §3.4.1 "significant mismatch". Hepsi alıntılanabilir.
- **A5 (gözlemci):** "Probe effect" adı ros2probe'dan; ama onların etkisi DDS/ağ düzeyinde, bizimki tracepoint + nsys + CPU çekişmesi. ros2_tracing <%15 gecikme overhead'i, LiMEIT <%1 core, ros2probe "not free". WiP overhead rakamı vermeli (split campaign).

Yenilik "faz var" değil, fazın trace'ten ölçülebilir tanımı (bring-up timer'ları, son ilk-execution) ve GPU tarafı (init skoru). Atıflarla kurulmalı.

### 3.8 İkinci turda okunan beş birincil metnin gap bölümüne etkisi

- **Abaza'24 birincil metni §3.3'ü doğruluyor ve keskinleştiriyor:** execution time = sched_switch ile sınırlanan CPU segmentlerinin toplamı; bekleme açıkça dışarıda ("the thread running it might get preempted or need to wait for data or a signal"). Yalnız tek-thread executor; attribution PID = node = thread; intra-process/waitable/action probe'u yok; ama client dispatch'i (P14) ve message_filters senkronizasyonu (P7, "&" düğümü) izleniyor. Draft'taki "client callbacks invisible upstream" cümlesi Abaza'yı istisna olarak anmalı.
- **Jiang'22:** analizciler executor *mekanizmasını* ros2_tracing ile doğruluyor ama iş yükü modelini verili alıyor; thread = ayrı işlemci ve wait_set overhead'i sıfır varsayımları Sobhani ile aynı. Vaka II (aynı ME grupta MT executor, 161→324 ms) bizim callback-group bulgusunun analitik gerekçesi.
- **Kim'25 (Cros-Rt):** "iki seviyeli hiyerarşi" derken kendisi üçüncü aktörü (kernel paket işleme thread'i, ksoftirqd, CFS'te) ortaya koyuyor; "executor = DDS participant = süreç" varsayımı bizim 8 süreç/15 executor gözlemiyle çelişiyor; hop gecikmesini thread başına (app/DDS/kernel) ayrıştırıp mesaj boyutuna regresyonla ölçüyor — bizim hop gecikmesi bulgusunun (A7) analitik kalıbı; "analizler alt katman gecikmelerini sabit ya da ihmal edilebilir sayar" eleştirisi §3.2 tablosundaki δ satırını destekliyor.
- **Bakita'24:** GPU scheduler'ın kendisi çok seviyeli (stream → channel → TSG/runlist → engine); context'ler (süreçler) arasında ~1–2 ms timeslice ile karşılıklı dışlama; CUDA context başlatma ~100 ms compute girişimi yaratıyor (A6 GPU init fazının donanım gerekçesi); channel sayısı (x86'da 8, Jetson'da 2–4) stream paralelliğini sınırlıyor ve Amert G2'yi düzeltiyor; "userspace kütüphanesi GPU ile doğrudan konuşur, bu yüzden kernel launch'ları izlemek zordur" (A5: gözlem noktası olarak nsys/CUPTI kütüphane düzeyi); üç önceki işin bound'ları yanlış varsayımla çöküyor (A3). Autoware'de GPU işi birden çok süreçten geliyor → context'ler arası timeslicing nsys'te görünmeyen bir scheduler katmanı; roadmap'e nvdebug ile runlist/channel durumu okuma eklenmeli.
- **Otterness'17:** Amert'17'nin öncülü; A3 için GPU tarafında sürüm kayması cümlesi ("memory access APIs … undocumented changes between software updates") ve A5 için X sunucusu anekdotu.
- **§3.3 düzeltmesi:** "extractors cover at most the OS and executor layers; none observes the GPU layer, and none observes multi-threaded executors" ifadesi beş metinle de tutarlı; Abaza artık birincil metinle doğrulanmış.
- **Liu'25 (ROS^RT):** executor katmanının deployment'a göre var/yok olduğunu gösteriyor (native wait set, events executor kuyruğu, ROS^RT dinamik worker havuzu) → H'de executor düğümü isteğe bağlı, callback→thread eşlemesi ölçülmeli (A3/A4). Native executor'ın hazır olmayan kayıtlı abonelikleri her refresh'te yoklaması (100 boş abonelik: 99p overhead 61→88 µs) bizim zero_exec entity gözlemine maliyet boyutu ekliyor (A7). ARS'de timer hizasızlığının iki girdili fusion'ı geciktirmesi join rol-bimodalitesinin gözlemsel karşılığı. DDS thread'leri süreç başına (A4 thread katmanı). "Çoğu executor değişikliği ROS sürümüne bağımlı" — Humble overlay'imiz için de geçerli.
- **Bédard'22 (ros2_tracing):** FISH'in temeli; iki fazlı handle-eşlemeli instrumentation bizim kimlik şemasının öncülü. Kendi future-work listesi FISH'in eklediklerini sayıyor: nesne yok edilişi, servis/action runtime olayları, middleware izleme; rclpy kör noktası ortak. "ROS 2 üst düzey scheduling yapar, OS trace şart" cümlesi A1'in 2022'deki hâli. Overhead referansı: 0.0033 ms/mesaj, 158 ns/tracepoint.
- **Li'23 (ROSGM):** A1 için en açık birincil alıntı ("ROS düzeyi, OS düzeyi, GPU sürücü düzeyi"); Problem 2 = GPU beklemesinin executor thread'ini tutması, extraction paragrafımızın kaynağı. Async modda GPU işi manager thread'ine, post-process CUDA runtime thread'ine taşınıyor → yönetim çerçeveleri H'yi değiştiriyor ve thread-local attribution'ı kırıyor (roadmap). Model verili, analiz yok; ihtiyaç duyduğu registration FISH'in ürettiği şey.
- **Enright'24 (PAAM):** A1/A3 için yönetim tarafından en net alıntılar ("analyses assume CPU-only", "unmanaged accelerator access → analysis results no longer hold"). Callback modeli zaten CPU/accelerator segmentlerinin ardışık dizisi (E_i, A_i, η_i) — FISH'in ölçmesi gereken biçim; koşullu graf bulgusu η_i'nin sabit olmadığını gösteriyor. Thm 1'deki spin/askı terimi CPU-time/GPU-wait ayrıştırmamızın analitik karşılığı. GPU işi başka süreçteki server executor'a taşınıyor → süreçler arası attribution (request UUID) gerekir; MT-4 her yöntemde 4×ST'den kötü. deep_analysis notunun PAAM iddiaları doğrulandı, "tam serileştirme" nüansı düzeltildi.
- **Li'22 (Autoware_Perf):** ros2_tracing üstünde e2e; architecture.json elle, member-variable (label) bağımlılıkları elle; mesajlar tek tek izlenemediği için e2e bağımsızlık varsayımıyla konvolüsyon (A7 join/veri-yaşı ile çelişir); ADE Docker'da LTTng olmadığından container dışına çıkılmış (bizim daemon'ın çözdüğü problem); GTX 1660 Ti'lı makinede GPU hiç anılmıyor (A1).
