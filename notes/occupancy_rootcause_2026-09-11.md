# Why the occupancy-grid callback gets *faster* under tracing (2026-09-11)
Generated by Claude Opus 5 (Anthropic)

Table 3 of the WiP paper reports the one metric that moves the wrong way: the
occupancy-grid callback's self-reported processing time falls from 3.69 ms
(untraced) to 2.75 / 2.79 ms (LTTng / LTTng+nsys) while its tail grows. This
note records what that turned out to be.

Data: campaign `overhead_aw_20260909_002310` (3 modes x 3 runs, diagnostics
only) and the traced session `fish_20260906_151532` (full trace + GPU, in PG).

## Answer

The callback's cost is **a blocking device-to-host copy of the costmap**, and
the length of that copy is set by how much GPU work *other callbacks* have
queued ahead of it. It is accelerator queueing delay, not compute.

Inside one invocation (traced session, steady state, n=217):

| | r |
|---|---|
| callback duration vs. duration of the blocking copy | **+0.90** |
| copy duration vs. foreign GPU work overlapping it | **+0.70** |
| copy duration vs. this callback's *own* GPU work | −0.17 |

| group | n | copy p50 | copy p90 | callback p50 |
|---|---|---|---|---|
| no foreign GPU work in the copy window | 197 | 2.26 ms | 3.69 ms | 3.12 ms |
| foreign GPU work present | 20 | 3.10 ms | 8.98 ms | 5.13 ms |

The foreign work is `lidar_centerpoint` — 131 kernels, 45.88 ms, attributed by
correlation id to centerpoint's callback windows in the same process
(`pointcloud_container`). Centerpoint's TensorRT inference and the occupancy
grid share one device and one process.

That explains every feature of Table 3:

* **the floor** (min 2.36 / 2.32 / 2.45, identical in all modes) is the copy
  with a free device;
* **baseline's broad 3.2–5.0 ms mass** is the copy queued behind centerpoint;
* **the traced spike** — 39 % of all traced samples in the single 2.6–2.8 ms
  bin — is the copy finding the device free, because tracing spreads the two
  GPU consumers apart in time;
* **the heavier traced tail** (6–8 ms: 1.9 % → 4.6 / 5.6 %) is the collisions
  that remain, now worse because centerpoint itself is slower (23.9 → 25.4 /
  26.2 ms).

So the metric that falls is the one measuring interference on a shared
accelerator — exactly the quantity the paper argues no ROS 2 task model
captures. It falls because the instrumentation perturbs the *phase* of two GPU
consumers, not because the node does less work.

## What it is not — each tested and rejected

| hypothesis | test | verdict |
|---|---|---|
| upstream delivers less often, so less work | rates overlap across modes (nsys run1 8.32 Hz vs baseline run3 8.30 Hz) yet p50 2.77 vs 3.64 | rejected |
| smaller input | output point counts through the whole filter chain differ by ≤1.5 % between modes | rejected |
| accumulation between invocations | r(gap since previous invocation, processing time) = −0.03 / +0.02 / +0.07 | rejected |
| the cloud arrives later, so a stamp-addressed TF wait collapses | within a mode the upstream pipeline latency swings 78 ms (p5 153 → p95 231) with **zero** effect on processing time | rejected |
| a cheaper GPU branch is taken | 200 of 219 traced invocations run the identical 10-kernel shape (`copyMapRegionKernel` x4, `prepareTensorKernel` x2, `fillEmptySpace`, `fillUnknownSpace`, `fillObstacles`, `applyBBF`), own GPU time 1.87 ms | rejected |
| measurement artefact | `autoware_utils::StopWatch` uses `Clock::now()` with sub-ms resolution; the measured region is the whole of `onPointcloudWithObstacleAndRaw()` | rejected |
| contention (more callbacks in flight) | in-flight count *at the invocation's start* is flat across duration buckets (1.1 → 2.0); the apparent 3.7 → 24.0 correlation was an artefact of counting spans that *overlap* a longer span | rejected |

Two earlier readings of my own were wrong and are corrected here: attributing
kernels by wall-clock overlap instead of correlation id (which credited
occupancy with centerpoint's TensorRT kernels and suggested a branch change),
and the pooled r=+0.75 between rate and processing time (a between-mode
confound — within each mode the correlation is zero).

## A second, separate finding: the warm-up pathology

`utils::getPose` and `utils::transformPointcloudAsync` both call

```cpp
tf2.lookupTransform(target, source, stamp, rclcpp::Duration::from_seconds(0.5));
```

i.e. a **blocking** lookup at the pointcloud's own stamp, and the callback
makes up to five of them before any GPU work. When the transform is missing the
call burns its timeout and the callback returns early — publishing no
processing time at all, so Autoware's own diagnostics never see it.

In `fish_20260906_151532` this costs the first ~10 s of the replay:

* centerpoint's first **10** invocations and the occupancy grid's first **6**
  take 1007–1034 ms each with **zero** GPU kernels;
* cause: localization is not up. `/tf` carries 5 messages in the 9 s before
  t=102.5 s and 1478 after;
* localization is late because of a chain of four nested blocking service
  calls — `autoware_automatic_pose_initializer` timer (7976 ms) →
  `/api/localization/initialize` (7971 ms) → `/localization/initialize`
  (7968 ms) → `ndt_align_srv` (**7920 ms**);
* the first successful invocations follow immediately: centerpoint at
  t=103.50 s, occupancy at t=103.72 s.

This sits entirely before phase (2), so it is absent from Tables 2 and 3 — in
the campaign runs phase (2) starts 5–7 s after the first `/clock` and the
warm-up window holds only 9–14 occupancy samples, max 5.5–17.1 ms. It is a
finding about the *phase definition*, not about the overhead numbers: "every
recurring callback has completed its first execution" is satisfied by an
execution that did no work.

## Note on Table 3's max column

Each max cell is a single sample out of ~180–190 per run, and the three maxima
sit at unrelated points in their runs (baseline #162/211, LTTng #78/182,
nsys #45/192). Dropping the first 50 executions of every run removes only the
nsys outlier (50.85 → 11.40) and leaves the other two untouched. p99
(8.92 / 9.80 / 10.23) is stable under every cut and tells the same story.
