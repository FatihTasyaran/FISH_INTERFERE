#1  ROS 2 intra-process path: the survey's "same executor" claim is wrong, and the double wake-up is unmentioned
---------------------------------------------------------------------------------------------------------------
Source: Tianze Wu, Weisong Shi, "Real-time Guarantee of Autonomous Driving Systems: State of the Art and Challenges"
(ACM survey), section on the intra-process path (their Fig. 5b).

What the survey says: intra-process communication is for nodes in the same process "(and therefore managed by the same
executor)"; delivery goes through waitable callbacks; subscribers are take_shared or take_ownership depending on whether
the callback takes a shared_ptr; zero-copy if no subscriber requires ownership; each subscriber has its own buffer
(owned / shared); the executor is notified when a message is enqueued.

Correct in the survey (rclcpp Humble/Iron):
  - delivery via SubscriptionIntraProcess, a Waitable: publish -> per-subscription ring buffer -> guard condition ->
    executor -> Waitable::execute() -> callback (callback_start carries is_intra_process=true); no rcl_take on this path.
  - buffer kind from the callback signature (rclcpp 16.0.19 = Humble, AnySubscriptionCallback::use_take_shared_method):
    ONLY the four shared_ptr<const Msg> variants (by value / const ref, with / without MessageInfo) -> shared buffer;
    everything else -> owned buffer: unique_ptr<Msg>, non-const shared_ptr<Msg>, and also const Msg& (the survey's
    "is it a shared_ptr" is right for Humble; my first reading that const Msg& is shared was wrong).
    SubscriptionOptions::intra_process_buffer_type (default CallbackDefault) can force SharedPtr / UniquePtr.
  - "specified when created": per entity, PublisherOptions / SubscriptionOptions use_intra_process_comm in
    {Enable, Disable, NodeDefault}; NodeDefault = NodeOptions::use_intra_process_comms (what Autoware's containers set).
  - copies depend on the subscriber mix: 0 ownership subs -> 0 copies; k ownership subs -> k-1 copies (the last one gets
    the original moved); mixed with >1 shared subs -> 1 shared copy + k-1. Nuance: a single ownership sub is also
    zero-copy; zero-copy needs publish(unique_ptr), publish(const Msg&) already makes one copy.
  - ring buffer depth = QoS history depth (keep_last semantics, oldest overwritten); keep_all and transient_local are
    not allowed with intra-process in Humble.

Wrong in the survey:
  - "same process, therefore same executor". The IntraProcessManager is per context (process-wide) and knows nothing
    about executors; a process may run several executors (rclcpp_components' component_container_isolated gives every
    component its own executor + thread and intra-process still works). In Autoware's /pointcloud_container it happens
    to hold: ONE component_container_mt (multi-threaded executor) hosts 21 nodes (notes/CRITICAL_autoware_intraprocess_
    waitables.txt) — by configuration, not by rule.

Real-time-relevant points the survey leaves out (both observed by FISH):
  a) executor dispatch class changes: a single-threaded executor takes ready work in the order timers, subscriptions,
     services, clients, waitables. The same callback is 2nd class on the DDS path and 5th class on the intra path.
  b) double wake-up: if the topic has ANY subscriber outside the process (rviz, rosbag record, topic_state_monitor, a
     non-intra sub), the publisher also writes to DDS (inter_process_publish_needed = subscription_count >
     intra_process_subscription_count). The same-process intra subscribers receive that DDS copy too: the executor
     wakes, rcl_take runs, Subscription::handle_message sees matches_any_intra_process_publishers(publisher_gid) and
     DISCARDS it silently. Per message the subscriber thread is woken twice, once for nothing.
     FISH evidence (fish_20261003_104424, fishwait12; notes/full_paper_todo.md item 11): occupancy map -> outlier filter
     (message_filters sub) had 246 discarded DDS takes 188 ms away from any callback window; before the fix 58 edges were
     paired on such discarded takes; after pairing by the intra path ipc_fifo edges went 32 -> 91 and rmw_take-paired
     3129 -> 3071.

FISH's own position to state next to it:
  - Humble has NO intra-process tracepoints (rclcpp_intra_publish, ring-buffer and buffer->ipb->subscription events
    arrived in Iron). FISH adds fish_rclcpp_intra_publish inside the library (PublisherBase::get_intra_process_
    subscription_count hook, per publish) and header-template hooks with the message address (intra_publish, intra_take)
    that need the application rebuilt.
  - pairing: mainline images FIFO at the consumer start; fork image fork-awintra1 (Autoware's 8 intra-process packages
    recompiled, 2026-10-05) by message address: 5,318 of 5,326 takes paired, 20 of 28 edges exact for every instance,
    3 edges without any address pair (open).
  - release of an intra-triggered instance = fish_rclcpp_intra_publish instant; kernel view: the waker of the subscriber
    thread is the publisher's thread (same vpid) for intra deliveries vs a Cyclone recv thread for DDS deliveries
    (ksched_split). Intra hop latency in the lidar chain: p50 0.1-0.2 ms, p90 ~1 ms.

Where in the paper: related work (cite the survey, correct the executor claim in one sentence), and the model/results
section as a finding FISH makes visible that the stock tools cannot (discarded DDS takes are invisible without the
is_intra_process flag + publish-side hook).

Follow-up (2026-10-19): does FISH see the take_shared / take_ownership choice and the intra-process enable?
  - intra enabled per SUBSCRIPTION: yes, indirectly. rclcpp emits rclcpp_subscription_init twice for such a sub (rcl
    handle -> SubscriptionIntraProcess waitable, then rcl handle -> Subscription), and FISH's fish_rclcpp_waitable_init
    (IntraProcessManager::add_subscription, node_handle = 0x0) marks the waitable; model_improved_pg joins them
    (141/141 on fish_20260816_165836).
  - intra enabled per PUBLISHER: only dynamically (fish_rclcpp_intra_publish fires); no registration event.
  - take_shared vs take_ownership: NOT recorded anywhere today (the fork's retention probe happens to run only in the
    take_shared branch, a side effect, not a record). The IPM's publisher->subscription matching is not recorded either.
  - where the information sits: IntraProcessManager::add_publisher / add_subscription / insert_sub_id_for_pub(sub_id,
    pub_id, use_take_shared_method) in rclcpp/src/rclcpp/intra_process_manager.cpp = COMPILED into librclcpp -> a
    library-side overlay patch (same class as fishwait12's publisher_base.cpp hook), no application rebuild, init-time
    only (zero steady-state cost). Proposed next fishwait step (fishwait25_ipm.py):
      fish_rclcpp_ipm_add_publisher(publisher_handle, pub_id, topic)
      fish_rclcpp_ipm_add_subscription(waitable, sub_id, topic, take_shared, depth)   (depth = ring buffer capacity
                                                                                        = actual QoS history depth)
      fish_rclcpp_ipm_match(pub_id, sub_id, take_shared)                              (insert_sub_id_for_pub)
    From the matches the model gets per intra edge the copy class of every publish: 0 copies if no ownership sub,
    k-1 if k ownership subs, 1 shared copy + k-1 when both kinds and >1 shared subs (IntraProcessManager::
    do_intra_process_publish). That is a static property the stock tools cannot state.

Result (2026-10-19, image fishwait25 = fishwait24 + docker/overlay_patches/fishwait25_ipm.py; functional run on the fork
fork-awintra2, session fish_20261019_170239, analysis ~/fish_traces/analysis_fork_awintra2, postprocess/ipm_report.py):
  - the IPM in 7 processes: 225 intra-process publishers, 143 subscriptions (129 shared / 14 ownership buffers),
    268 publisher→subscription matches; 76 of the 143 subscriptions have a matched publisher (the rest are fed over
    DDS or not at all: /clock, /parameter_events, topics without a same-process publisher).
  - copy class: ALL 268 matches are zero-copy. The 14 ownership subscriptions (unique_ptr callbacks: the 4
    distortion_corrector nodes + …) are the only subscriber of their topic, so the IPM moves the message (0 copies).
    No publisher in Autoware's logging_simulator ever copies on the intra-process path — a static statement FISH can make
    and the stock tools cannot.
  - the "same process ⇒ intra" trap, measured: voxel_based_compare_map_filter shares the pointcloud_container with its
    publisher but is NOT registered in the IPM (intra-process disabled for that component) → DDS in-process. Our own
    extractor had that edge wrong until the IPM events existed. Worth one sentence next to the survey correction.
  - lidar_centerpoint: shared buffer, depth 5, 247 takes; the two edges are paired (fork needed cuda_blackboard rebuilt).
