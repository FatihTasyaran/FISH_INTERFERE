# From the FISH graph to FISH tasks (typed-EDD) and to LiME-IT-style traditional tasks
Generated by Claude Fable 5.1 (Anthropic), 2026-10-04. Design note written before the extractor
(`postprocess/extract_fish_tasks.py`, `postprocess/limeit_models.py`). Sources read in full:
Aromolo et al., "Event-Driven Delay-Induced Tasks", RTAS'21 [EDD-1]; Srinivasan/Günzel/Nelissen, "RTA for
Limited-Preemptive Self-Suspending and EDD Tasks", RTSS'24 [EDD-2]; Ye/Marković/Brandenburg, "Framework-Agnostic
Model Inference for Intra-Thread Real-Time Tasks", RTAS'26 [LiME-IT]; model section of the old FISH draft.
Supersedes the boundary rule of notes/design_task_model_from_ft.txt (Aug) where they differ; keeps its decisions
(task ≠ callback, join = deposits + merge, executor carried on every job, chains carry deadlines).

## 1. What the target model asks for
EDD-1: task τ = (G, T, D, π), G = (V, E) a DAG. Vertex = subtask with WCET C. Edge (a,b) carries [W_min, W_max]:
b is *ready* once a has completed AND a delay in that interval has elapsed (the delay = waiting for an event
notification). One source vertex (C = 0) = the job release; all subtasks of a job are released together; a vertex
with several incoming edges needs ALL of them (AND). Sporadic with minimum inter-arrival T; fixed priority π; each EDD
task lives on one processor, a parallel task spread over processors is a *set of synchronously released EDD tasks*,
one per processor, cross-processor predecessors replaced by a source edge (0, R*).
EDD-2: same graph, vertices carry [C_min, C_max], edges [sus_min, sus_max]; *known arrival pattern* (periodic, bursts,
multi-rate …) so the analysis works on the finite JOB SET of an observation window, J = ([r_min, r_max],
[C_min, C_max], d, p, pred); segments are non-preemptive, scheduling is global job-level fixed priority on m cores;
each segment may have its own priority/deadline.
"Typed" (typed-DAG / HPC-DAG sense): every vertex also names the resource class that executes it.

So a typed-EDD task needs: (i) segments and their resource, (ii) [C_min, C_max] per segment, (iii) precedence with
[δ_min, δ_max] per edge, (iv) an arrival pattern at the source, (v) scheduling attributes (priority, processor /
server), (vi) D. FISH observes (i)–(v); D is a requirement, not an observable (§6).

## 2. Definition — FISH task
A FISH task is τ = (G_τ, A_τ, Σ_τ) with G_τ = (V_τ, E_τ) a DAG of *segments*:
- segment v = (F(v), θ(v), ρ(v), [C_min, C_max], B(v))
  F(v): the F-layer vertex of the FISH graph it belongs to (callback, publisher thread, GPU function);
  θ(v) ∈ {exec (callback code on an executor thread), helper (OpenMP/pthread worker), mw (middleware thread),
          sm (GPU compute), ce (GPU copy engine)} — the type;
  ρ(v): the concrete resource: EX vertex + callback group (+ thread set, policy/priority/affinity from the thread
        snapshot) for CPU types; (device, stream) for GPU types;
  C: *on-CPU* time of the segment (sched_switch split), not the window length; GPU: activity duration;
  B(v): contended-lock waiting inside the segment (futex class `lock`), kept as an attribute, not as a delay.
- edge e = (u, v, κ, [δ_min, δ_max], prov): v becomes ready δ after u completes.
  κ ∈ {dds, intra, srv_req, srv_resp, join, seq, gpu_launch, gpu_sync, omp_fork, omp_join, timer}.
  prov ∈ {measured, inferred} (the tier decides, §7).
- A_τ: arrival pattern of each source vertex (§4.4).  Σ_τ: the executor-level scheduling context (§4.5).

Task boundary rule. Edges of the FISH graph fall in two classes:
- TRIGGER edges — the consumer instance exists *because* of the producer instance: sub edges whose subscription
  callback is dispatched (DDS or intra-process), service request → server callback, response → client continuation,
  join deposit → merge, everything inside a callback (GPU, OpenMP, sequence).
- SAMPLED edges — the consumer runs anyway and reads whatever is there: polled-msg (take() inside the reader),
  inferred state links (deposit callback + read elsewhere), tf lookups.
A FISH task is a weakly connected component of the data-phase F-layer over TRIGGER edges on data topics. SAMPLED edges
never belong to a task: they are *inter-task data dependencies* labelled with the measured data age and are what
cause-effect chains (reaction time / data age) are made of. This is the EDD reading of ROS: precedence-with-delay
inside a task, register-style communication between tasks. (Aug rule: "state edges excluded" — same thing, now with
the reason.)

Strict EDD task vs component. If the component has one source it is a single-rate EDD task (T = source period).
Several sources (three lidars into concatenate; IMU + twist into gyro_odometer) give a multi-source component: no
single T, AND-joins across independent arrivals. FISH keeps it as one task with one arrival pattern per source and
resolves it at JOB level (EDD-2's job set), where each merge job's `pred` is the deposits it consumed — today an
APPROXIMATION (deposits since the previous merge): message_filters / the concatenate collector match by header stamp in
application memory, there is no collector id in the trace (notes/join_semantics_from_traces.txt:89-92; exact only with
the message_filters hook, todo A0.5e). prov = inferred on every join pred.
OR vs AND. A ROS subscription callback instance consumes exactly ONE message. Several trigger in-edges on one vertex
(two publishers of one topic, an OR-relay, the two delivery paths of a sub) are therefore ALTERNATIVES: each job has one
predecessor. EDD's multi-in-edge AND exists in ROS only inside a join's merge. A FISH task template is thus an EDD
graph with OR-activated vertices; a strict EDD task is obtained per job (the job DAG has AND/single predecessors only),
which is exactly the level EDD-2's analysis works on. The extractor tags every vertex: timer | single | OR(k) |
AND-join(merge inside)+OR | source.

## 3. Where each piece of a callback goes
A callback F is not one EDD vertex. The EDD delay is counted from the *completion* of the predecessor, while a ROS
callback publishes in the middle, blocks on the GPU, and forks OpenMP teams. F expands into a small segment DAG
H_F (the old draft's "function layer induces one DAG per entity" — now with measured cut points):
| cut point inside the window | what it creates | observable |
|---|---|---|
| publish of a trigger topic at t_p | segment boundary; the outgoing dds/intra edge leaves the segment ending at t_p; tail [t_p, end] is a successor segment (seq, δ=0). If the tail is negligible (p99 < 50 µs) no split: "publish-at-end" | rcl_publish / fish_rcl_publish / fish_rclcpp_intra_publish inside the window |
| blocking GPU sync (cudaStreamSynchronize …) | CPU segment → sm/ce vertices (gpu_launch, stream FIFO) → next CPU segment (gpu_sync); collapsed EDD form: one seq edge with δ = [GPU wait min, max] — exactly EDD-1 Fig. 3. CAVEAT: the measured wait contains OTHER processes' GPU work (occupancy's blocking D2H copy correlates +0.70 with centerpoint's GPU load, −0.17 with its own: notes/occupancy_rootcause_2026-09-11.md) — the collapsed δ is contention-dependent, not a property of the task; an analysis under GPU sharing needs the typed form (sm/ce vertices contending on the device). GPU work launched in one callback and synced in a later one (the Apr-2026 "73 %" figure predates the clock fix; r7 showed 0 kernels after the callback end) is attributed by stream ownership, never by wall-clock overlap | CUPTI runtime + kernel activities; futex class `gpu` |
| OpenMP parallel region | fork → (k−1) helper vertices + the master's own part → join | shim fish_gomp_parallel(_end), helper on-CPU (assist_region), futex class `omp` |
| synchronous service wait / sleep / I/O | seq edge with δ = [sleep min, max] (self-suspension) | sched_switch state S/D outside futex-lock |
| contended lock | NOT a cut: B(v) | futex class `lock` |
| preemption / runnable | NOT a cut, not in C: it is interference, the analysis' output | sched_switch R/R+ |
Level of detail is a knob: L1 = one vertex per callback with C = on-CPU and S = total self-suspension [min, max]
(dynamic self-suspending form, EDD-1 Thm. 1 gives the same reduction); L2 = the segment DAG above. L1 is what every
session supports; L2 needs the kernel session (+ shim, + nsys for GPU callbacks).

## 4. Extraction procedure (graph → tasks)
1. Scope. F vertices with phase = data (mark_phases), edges on data topics (topic_class); init/shutdown instances and
   infra topics are out. Publisher threads (ptype thread: rosbag player, driver I/O threads) and ext: sources are
   kept as sources.
2. Edge classes. sub edge with dispatched callback → trigger (κ = intra if flow method ipc_fifo/ipc_time, else dds);
   srv → trigger pair (req, resp); join edge member → completer → trigger (join); polled-msg / state / tf → sampled.
   A sub edge whose target callback never fires (polling S) is the first half of a sampled dependency. The graph and
   the extractor output keep S explicit (C6, Fatih 2026-10-03: pub → S sub edge, S → R polled-msg edge); the task-level
   dependency "writer task ⇢ reader task, age" is derived from the pair, S is never dropped.
   A hop INTO a deposit-only callback is a trigger (the deposit is a real, cheap job); the sampled edge is the one from
   the deposit to its reader (the component view's "sampled coupling" is this pair seen from one level up).
3. Components over trigger edges → tasks. Sources of a task = vertices with no incoming trigger edge: timers,
   publisher threads / ext, callbacks fed only by sampled edges.
4. Arrival A_τ per source: timer → periodic (T from rcl_timer_init; wall T = T/rate under sim time; offset and jitter
   from the observed starts); thread/ext source → the observed publish sequence → sporadic (min inter-arrival, arrival
   curve) or periodic fit (§5).
5. Labels. C per vertex from the sched split (min / p50 / p99 / max over steady-state instances); δ per edge:
   dds → transport = arrival (fish_dds_rhc_store) − publish, measured at tier max; upper-bounded by take − publish at
   tier default (prov = inferred); intra → 0 by construction (ready at the publish instant); srv → request/response
   transport; gpu_sync → GPU wait; timer → 0.
   Relation to the 2026-10-03 definition "release = publish instant of the consumed sample" (todo A0.1): that is the
   completion of the predecessor segment (event origin); the EDD READY instant of the consumer is the arrival, i.e.
   publish + δ. Both are kept per job edge: rts (start − publish, the old attribute) = δ + (start − arrival).
   What is NOT a delay: arrival → callback start. That is executor dispatch + OS scheduling = the response-time
   component an analysis must *predict*; FISH reports it per vertex as the measured ready→start (rts_*) to validate
   the analysis, never as part of δ.
6. Scheduling context Σ. Per vertex: executor kind (ST / MT n threads), callback group and its type (mutually
   exclusive / reentrant), thread policy / priority / affinity. Inside an executor the dispatch order is the rclcpp
   wait-set order (timers, subscriptions, services, clients, waitables; registration order inside a kind) — derived
   from the *_init / add_cbgroup event order (inferred, non-preemptive polling-point semantics).
7. Jobs. Instance k of a task = one release of a source and everything it triggered, linked by message identity
   (DDS: publish ts ↔ source_timestamp of the take; intra: FIFO; srv: sequence number). Each job vertex carries its
   measured ready / start / finish / on-CPU; each job edge its measured δ. The job set of the observation window is
   the EDD-2 input; the template [C_min, C_max], [δ_min, δ_max] is the aggregate over jobs. Conditional behaviour
   (a publish that does not happen, a GPU shape that changes, a join completed by the timeout) shows up as job DAGs
   with different vertex sets: reported as shape classes with counts, not averaged away.
8. Joins. Members d_i (deposit segments, one per input callback) → merge segment m (κ = join, δ = 0), m on the
   executor of the completing input; timeout timer → m as the alternative release. At job level `pred(m)` = the
   deposits actually consumed. Template: AND-join flagged `timeout_alt`.
9. Middleware. Cyclone recv threads are tasks of type mw (sporadic, released by network arrivals); a dds edge can be
   refined to publisher segment → recv vertex (C = per-sample receive cost) → consumer, when their demand matters.

## 5. LiME-IT-style traditional tasks from the same data
LiME-IT's observation model: per intra-thread task (ITT) the start s_i and finish f_i of every invocation, plus the
executor thread's suspend/resume; release unknown → window R_i = [W(s_i), s_i], W = last wake-up of the thread
outside every ITT window; models: periodic (Φ, T, J) as possible-fit (PF) / certain-fit (CF), sporadic as arrival
curves α⁺/α⁻ with over/under approximations; execution time = processor time between start and finish.
FISH records a superset: s_i, f_i (callback_start/end) per callback *handle*, thread wake-ups (sched_waking, exact
rcl_wait exit at tier max), on-CPU per instance. Therefore:
- T_LiME(F): run LiME-IT's own inference (reference library `rt-model-inference`, else Listings 1–3 re-implemented)
  on FISH's (s_i, f_i, W) → periodic PF/CF + arrival curves per callback, *named* by node / entity / symbol.
- T_FISH(F): same model class with FISH's *point* releases (timer: expiry grid; data-triggered: arrival instant) →
  jitter without the release-window pessimism. PF ≤ point ≤ CF is the expected order; the gap is what the missing
  release costs LiME-IT.
What is given up by going traditional: precedence and delays (the DAG), the typed GPU/helper segments, joins, the
trigger-vs-sampled distinction, multi-threaded executors. What it buys: a direct comparison with LiME-IT.
Comparing the task SETS without running LiME-IT (it needs eBPF + perf as root; not available here) — computable from
the FISH model: (a) callbacks on multi-threaded executors (outside LiME-IT's scope); (b) callbacks sharing an entry
symbol with another callback on the same thread (one ITT for N FISH callbacks — the reference system needed a template
tag to avoid this); (c) callbacks living in dlopen'ed component libraries (LiME-IT Rule 3 must be disabled);
(d) callbacks with too little CPU time to be sampled at 10 kHz in 30 s; (e) what LiME-IT sees and the F layer does
not: rclcpp-internal ITTs (timer management, message propagation) and non-executor threads — FISH has the latter as
middleware/publisher threads.
Direct check (stretch): the ROS 2 reference system (LiME-IT Table I) under FISH → same 29 callbacks? same periods?

## 6. What stays outside the trace
Deadlines D (requirement; chain-level; candidates = Autoware's own timeout parameters). WCET in the static sense
(C_max is the observed maximum over the window — measurement-based, load-dependent). Inferred state links
(memory reads). message_filters internals (join by signature, not by code).

## 7. Tier dependence (which labels are measured vs inferred)
| quantity | max | default | min |
|---|---|---|---|
| ready instant of a data-triggered instance | rhc_store arrival / intra publish | publish instant (source_timestamp) + kernel wake of the executor thread | first take in time order |
| δ(dds) | measured transport | ≤ take − publish (inferred upper bound) | — |
| identity of a DDS sample (publish ↔ take) | exact: writer GUID + source timestamp (fish_dds_write, fishwait19+) | exact (same event is in the default tier) | — |
| message size, publish duration | fish_dds_write | fish_dds_write | — |
| executor sleep/wake | rcl_wait enter/exit | kernel sched_waking + "sleep outside a window" | — |
| C split | kernel session (any tier) | same | window length only |
| OpenMP membership | shim regions | shim regions | — |
