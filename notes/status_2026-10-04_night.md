## INCIDENT found tonight — the OpenMP shim changed what the application computes (fixed)
`libfish_gomp_shim.so` (fishwait16–18) resolved the real `GOMP_parallel` with `dlsym(RTLD_NEXT, …)`. In a process that
dlopen()s its node library (every rclcpp_components node_main executable and every component container) libgomp sits
in the library's LOCAL scope, the lookup returned NULL and the shim skipped the region body. Evidence: NDT's parallel
regions lasted 0.5 µs (p50) with num_threads = 4; NDT logged "Score is below the threshold. Score: 0" 28× per run and
its sensor callback used 0.9 ms CPU instead of ~5 ms + helpers. This is the "NDT anomaly" of the 2026-10-03 EOD note, and
the "2 M serial regions of 0.2 µs" finding of that note was the same artefact — RETRACTED.
Affected sessions (functionally invalid for anything downstream of an OpenMP region): every shim run —
fish_20261003_173023 (fw17 max, yesterday's report), fish_20261003_220452 (fw18 max pinned, tonight's first run), and the
aborted fw16/fw17 runs. Structure (graph, tasks, edges) of those sessions is still usable; execution times of
NDT / euclidean_cluster / other OpenMP users are not.
Fix: the shim links libgomp itself, falls back to an explicit dlopen, and aborts loudly instead of skipping
(docker/overlay_patches/fish_gomp_shim.c). Regression test docker/overlay_patches/test_gomp_shim.sh reproduces the
dlopen case: old shim → 0 threads ran the region, new shim → 4. First fixed run (fish_20261003_223657): 0 "Score is
below" warnings. How it was found: the extracted task set showed NDT with C p50 = 0.92 ms — the sanity check the user
asked for ("do the extracted tasks show anything contrary to what we know of Autoware").
Lesson recorded in task_model_gaps.md: a run-validity gate must include a FUNCTIONAL check (the traced application
computes what the untraced one does), not only liveness/loss counters.

Things the extracted tasks show that the "textbook" Autoware picture does not:
1. Publishing is neither cheap nor at the end. /sensing/lidar/top/pointcloud_raw_ex is 6.7 MB per scan; the DDS write takes
   29.5 ms (p50) INSIDE the driver callback and the sample reaches its two DDS readers 38 ms (p50; max 177 ms) after the
   publish — while the in-process consumer started 0.1 ms after the intra-process publish, 35 ms before the driver callback
   ended. The two DDS readers are traffic_light_occlusion_predictor instances that spend 0.00 ms on it. (Reliable QoS +
   WhcHigh 500 kB in Autoware's Cyclone XML → the writer is throttled by the readers.) Also obstacle_segmentation/pointcloud:
   1.1 MB, write 5.7 ms. Velodyne packets: top 760 kB, left/right 91 kB (the "1.4 MB" used in earlier notes was wrong).
2. The three lidars are not synchronous: top 207.5 ms, left/right 200.0 ms wall (9.64 vs 10 Hz in bag time). The join is
   completed by top in 86–89 % of the frames, by left in the rest, never by right; downstream periods are ~201 ms with
   340 ms "jitter" (a beat pattern), so every downstream callback classifies as sporadic, not periodic.
3. Join callbacks are bimodal by role (now a vertex attribute): concatenate top deposit 0.02 ms / complete 8.3 ms.
4. 12 (node, topic) pairs have two subscriptions, one dispatched and one polling (VehicleStopChecker next to an

5. centerpoint: 3.8 ms on-CPU, 23.6 ms blocked in the CUDA sync per invocation (max 1.03 s) — a self-suspending vertex; NDT:

6. rmw's discovery thread takes ros_discovery_info 233 k times per session on threads that never run a callback — middleware

## Segment level (L2) — validated on fish_20261004_015212
ksched_split stores, per instance, its blocked intervals with a class (g = blocking CUDA runtime call, o = OpenMP barrier,
s = sleep, d = uninterruptible; contended locks stay blocking B); extract_fish_tasks turns the dominant class sequence of a
callback into a segment template with min/p50/max per segment and suspension. Cutting at every kernel-level wait was too
fine (the CUDA driver waits ~18 times inside one call), the cut is the CUDA CALL.

varying number of blocking calls per frame — for it the stable description is L1 (C plus total GPU suspension [min, max],
the dynamic self-suspending form), or the typed DAG per invocation (gpu_dags). C_k is wall time of the chunk, not on-CPU.
